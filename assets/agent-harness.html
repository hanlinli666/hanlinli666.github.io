0太长不看

  • Harness 是包裹在模型之外、决定模型「看到什么、能做什么、结果如何被使用」的整个工程系统：prompt、工具、循环、上下文管理、解析、沙箱……
  • Agent = Model + Harness。同一款模型换一套 harness，benchmark 分数可以差出一大截。
  • 榜单上的分数从来不只是模型的分数，而是「模型 × harness」组合的分数。
  • 后训练（尤其 RL）会把 policy 「焊」在训练时的 harness 上 —— 这叫 harness 锁定，伴随 entropy collapse、context anchoring 和 OOD 退化。
  • 下一站：harness-agnostic 的 agent 后训练 —— 把 harness 差异当作需要泛化的环境噪声。

1缘起：从一个马的名词说起

harness 的本义是马具 —— 套在马身上、让蛮力为人所用的那套皮带与缰绳。马再壮，没有马具也拉不了犁；力气如何被引导、约束、分配，全看这套装备。

软件工程里早就有这个词：test harness（测试治具）。它指的不是测试逻辑本身，而是那套「把被测物架起来、喂输入、收输出、监控行为」的脚手架。硬件测试里的夹具同样叫 harness。

LLM 社区完整继承了这层含义，并把它扩展成：

Harness = 包裹在模型之外、决定模型如何被调用的整个工程系统。它决定模型看到什么（上下文）、能做什么（工具）、怎么做（流程约束）、做错了怎么办（容错）。

一句话记法：模型是发动机，harness 是整辆车 —— 方向盘、变速箱、仪表盘、安全带，一个都不能少。

2Agent = Model + Harness

这个等式是理解当下 agent 生态的关键视角。它说的是：你使用的「agent」从来不是模型本身，而是「模型 + 一整套工程系统」的复合体。换个说法：换模型是换引擎，换 harness 是重新调整辆车的操控。

三个思想实验：

  1. 同一个模型，裸 API 只能聊天；接上工具、沙箱和循环，就能修 bug、跑数据 —— 差的是 harness。
  2. 同一个模型，两套不同的工具命名与描述，工具调用成功率可以明显不同 —— 差的还是 harness。
  3. 同一个模型、同一个 benchmark、两套 scaffold，分数差异可达 1.5 倍甚至数倍 —— SWE-bench 社区的共识是：不同 harness 的结果不可直接比较。

视角切换「模型强不强」和「agent 好不好」是两个问题，中间那根传动轴就是 harness。评估一个 agent 产品时，先拆开看：哪些能力来自权重，哪些能力来自缰绳。

3解剖一只 Harness

一只典型的 agent harness 长这样（自下而上调用模型，自上而下约束模型）：

┌─────────────────────────────────────┐
│            Agent Harness            │
│  ┌───────────────────────────────┐  │
│  │ 指令层：system prompt / 流程   │  │
│  ├───────────────────────────────┤  │
│  │ 工具层：schema + 描述 + 注册   │  │
│  ├───────────────────────────────┤  │
│  │ Agent Loop：控制流与终止条件   │  │
│  ├───────────────────────────────┤  │
│  │ 上下文管理：裁剪 / 摘要 / 预算 │  │
│  ├───────────────────────────────┤  │
│  │ 解析与容错：结构化输出 / 重试  │  │
│  ├───────────────────────────────┤  │
│  │ 沙箱：执行环境与权限边界       │  │
│  ├───────────────────────────────┤  │
│  │ 记忆 / 状态 / 可观测性         │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘

3.1 指令层：模型的「出厂设置」

  • 系统提示词：角色设定、工作流程、安全约束、输出格式，是 harness 中最常被低估的组件。
  • few-shot 示例：示范「好的轨迹长什么样」，等价于在推理期做了一次轻量对齐。
  • scratchpad 约定：规定思考区、行动区、观察区如何组织（ReAct 格式就是最经典的约定）。

很多「模型变笨了 / 变聪明了」的观感，其实是 prompt 层改动带来的行为漂移。

3.2 工具层：模型的双手

  • Function Calling：以 JSON Schema 声明工具的名称、描述与参数，模型生成结构化调用。
  • 设计维度：粒度（大而全 vs 小而正交）、数量、命名、描述质量。工具描述改几个词，调用成功率就可能波动 —— 模型对工具文本极度敏感。
  • 报错也是接口：错误信息是写给模型看的，要可读、可定位、可行动。No such file 远不如 No such file: src/util.js. Did you mean src/utils.js? Run ls to list files.
  • MCP（Model Context Protocol）：把工具/资源接入标准化为 server/client 架构，一次接入、处处可用。它本质上是「harness 接口层」的标准化努力。

3.3 Agent Loop：心脏起搏器

几乎所有 agent 的核心都是这个循环：

while not done and steps < MAX_STEPS:
    resp = llm(messages, tools)        # 思考 + 决策
    if resp.has_tool_call:
        obs = sandbox.execute(resp.tool_call)  # 行动
        messages.append(obs)           # 观察
    else:
        done = True                    # 模型认为完成了

关键设计点：

  • 终止条件：自然停止、强制截断、预算（token/步数/时间）耗尽。
  • 防打转：检测重复动作、重复观察，及时注入提示或强制换路。
  • 编排形态：单 agent 大循环 vs 多 agent 分工（planner / executor / critic），本质都是在改这个循环的结构。

3.4 上下文管理：稀缺资源的分配器

  • context window 是硬预算：system + 工具定义 + 历史 + 观察 + scratchpad 六方争抢。
  • 最膨胀的往往是观察（一条命令输出几千行）→ 需要截断、折叠、摘要。
  • 高级策略：把长内容外置到文件系统，用 grep / read 按需取回（Claude Code 的经典做法）—— 等于给模型一个「硬盘」当扩展记忆。

要点上下文管理策略决定了「模型所处的世界」长什么样。它不是性能优化，而是世界观设计。

3.5 输出解析与容错：翻译官 + 安全气囊

  • 结构化输出：JSON mode、structured outputs、grammar 约束（如 GBNF），把「希望模型守格式」变成「格式上不可能出错」。
  • 解析失败三连：重试、修复（截断补全 / 正则抢救）、降级（退回纯文本）。
  • 参数校验：工具调用参数过 schema validation，脏输入不进沙箱。

3.6 沙箱与执行环境：世界，也是围栏

  • 代码执行：容器 / microVM、超时、CPU 与内存限制。
  • 文件系统与网络权限：只读挂载、出口白名单。
  • harness 是 agent 的全部世界；沙箱边界就是世界的边界。同一个模型在不同沙箱里的「能力」，其实测量的是不同的世界。

3.7 记忆、状态与可观测性

  • 短期记忆 = 对话历史本身；长期记忆 = 文件 / 向量库 / 外部存储。
  • 状态：任务清单（todo list）、中间产物（patch、diff、日志）。
  • 可观测性：轨迹日志、回放、token 与成本统计。debug 一个 agent = debug 它的 harness + debug 模型，没有日志寸步难行。

4经典 Harness 巡礼

4.1 ReAct：祖师爷（2022）

用纯文本约定出 Thought → Action → Observation 的循环协议，把「推理」和「行动」交织进同一个上下文。今天所有 agent loop 都能看出它的影子。

4.2 CodeAct：用代码当动作（2024）

把「动作」从 JSON 换成可执行代码。一个代码块可以组合多个动作、传递变量、写循环 —— 表达能力直接拉满。现代编码 agent（Claude Code、OpenHands 等）的主流范式都受它影响。

JSON 动作（ReAct 式）代码动作（CodeAct 式）
单步表达力一个动作任意长的动作序列
状态传递靠上下文复述变量直接复用
出错成本低（结构受限）高（代码可能有 bug），需要沙箱兜底

4.3 SWE-agent 与 ACI：接口设计学的开山（2024）

SWE-agent 提出 ACI（Agent-Computer Interface） 概念：正如 GUI 是为人类设计的接口，工具与反馈也应该专为 agent 设计。核心组件：

  • 简洁的文件浏览器（每行带行号、限制输出行数）
  • 带滚动窗口的编辑器 + 编辑后自动 lint（信号前置）
  • 防呆设计：危险命令给出信息丰富的报错，而不是静默失败

结论极其震撼：模型不变，仅优化 ACI，SWE-bench 解决率成倍提升（论文中 GPT-4 达到全集 12% 量级，而朴素接口设计几乎不可用）。这是「harness 值多少分」最著名的定量证据。

4.4 工业界与 MCP：缰绳的产品化与标准化

  • Claude Code / Codex CLI / 各类 coding agent：harness 即产品。产品间的体验差异，大部分来自缰绳而非引擎。
  • OpenHands（原 OpenDevin）：开源 agent 基础设施的代表，适合逐行研读学 harness 工程。
  • MCP：把工具接入标准化，让「换缰绳」更容易 —— 也让人看清：模型能力 ≠ 生态能力。

学习建议各家 agent 的 system prompt 很多已公开（Claude Code、OpenHands 等），是最好的 harness 设计教材。读三份，对比它们如何组织指令、工具与上下文。

5Harness 与评测的罗生门

5.1 分数到底是谁的分数

榜单报的永远是 (model, harness) 二元组的分数。SWE-bench 官方长期强调：不同 agent scaffold 的结果不可直接比较。裸模型的 pass@k 和套上 harness 后的 resolve rate，是两种完全不同的测量。

看分数前先问三件事：用了什么 scaffold？给了哪些工具？上下文怎么管理？答案不明的分数，参考价值存疑。

5.2 评测环境泄漏（harness leakage）

  • 定义：后训练所用的 harness 与评测 harness 一致或高度相似，导致分数虚高。
  • 极端形式：在评测同款 scaffold 上做 RL，等于把测试环境搬进了训练环境。
  • 灰色地带：如果真实部署环境就是评测环境，这算「对齐」还是「作弊」？社区至今没有共识，但趋势很明确 —— 必须披露。

5.3 Minimal mode 的启示

社区曾观察到一类现象：某些模型的「极简工具模式」在特定基准上反超自家「满配模式」—— 工具更少，分数更高。一种解释是：RL 训练锁定的就是那套极简 harness，其 observation 分布与 action schema 和评测环境高度对齐；满配模式反而把模型推入了 OOD 区。

教训报分数必须报 harness 配置；做对比实验必须控制 harness 变量。否则你测的不是模型，而是「模型和某根缰绳的默契度」。

6Harness 与后训练的暗面

6.1 RL 环境即 harness

Agent RL 的「环境」= 沙箱 + 工具集 + loop 结构 + 奖励函数 —— 每一项都是 harness 组件。因此 policy 学到的不只是「怎么解题」，还有「在这个 harness 里怎么解题」。训练环境的每一个工程细节，都会被梯度默默写进权重。

6.2 Harness 锁定（harness locking）

定义：policy 的行为分布过拟合于训练 harness 的特定 observation 格式与 action schema。典型症状：

  • 换一套 harness（哪怕公认更好用），分数不升反降；
  • prompt 模板稍作改动，成功率明显下滑；
  • 工具偏好固化：明明有更合适的工具，仍反复调用训练期常用的那个。

6.3 Policy / Entropy Collapse：分布越训越尖

自生成轨迹 + 窄环境 + 强奖励信号，会让动作分布的熵急剧收缩：模型只走那几条「在训练环境里被证明有效」的路，探索性丧失，遇到新环境极度脆弱。这与 RLHF 中反复被观察到的 entropy 崩塌同源 —— 优化压力总在「榨干」分布的多样性，而窄 harness 把这个过程加速了。

6.4 Context Anchoring：缰绳成了「第二权重」

policy 会学会依赖特定的上下文组织方式：历史的排列、系统提示的措辞、观察的格式。上下文稍有重组，模型表现判若两人。本质上，harness 成了 policy 的第二套参数 —— 只不过它不在权重里，而在工程代码里。权重你可以 checkpoint，缰绳可没有版本管理。

6.5 为什么现在才显形

  • 模型规模与训练数据多样性仍在上行，RL scaling law 尚有余量，锁定被「能力增长」掩盖；
  • 评测维度长期单一，harness 敏感性不是显学；
  • 随着 agent RL 规模化（Klear-AgentForge 等训练环境工作涌现），训练 harness 的多样性和评测 harness 的披露问题会越来越刺眼。

7走向 Harness-agnostic 的后训练

核心思想：借用机器人领域的 domain randomization（sim2real 的经典技巧）—— 训练时把环境随机得越狠，部署时越稳。对 agent 来说，harness 就是那个需要被随机化的环境。

随机化组件

训练期随机变换 prompt 模板、工具命名与描述、观察格式、上下文裁剪策略，让 policy 不绑定任何特定文本形态。

多 harness 混合 rollout

多套 harness 交替采样轨迹，等价于对「环境表面形态」做数据增强。

评测矩阵化

报告 model × harness 矩阵而非单点分数；方差本身就是重要的能力指标。

泛化即目标

把「对 harness 的不敏感性」直接作为训练目标或评测维度来优化。

终局想象：模型像适应不同操作系统一样适应不同 harness —— 换根缰绳，照样跑得又快又稳。

8好 Harness 的设计原则

以下原则大量借鉴 SWE-agent 的 ACI 设计经验，加上工程实践的总结：

  1. Token 效率优先：每一屏观察都要「值回票价」。模型读上下文是要花预算的，废话就是税。
  2. 信号前置：lint、类型检查、单测即时反馈，别让错误攒到最后爆炸。
  3. 动作空间小而正交：工具少而精，命名自解释，一个工具只做一件事。
  4. 报错给模型看：错误消息要可读、可定位、可行动 —— 它是 harness 里信息密度最高的 prompt。
  5. 防呆不防手：危险操作要摩擦（确认 / 备份），正常操作要丝滑。
  6. 可复现：轨迹可回放，随机性可固定 —— 否则 debug 是玄学。
  7. 失败要体面：超时、死循环、预算耗尽都要有优雅出口，而不是留下半摊子烂摊子。

10一页总结

  • Harness 不是模型的附属品，而是 agent 的另一半；Agent = Model + Harness 是理解一切 agent 问题的第一公式。
  • 看分数先问 harness，做训练先防锁定，写工具先想「模型读起来累不累」。
  • 评测的公信力取决于 harness 披露；后训练的上限取决于 harness 多样性。
  • 未来的核心能力之一：让模型在任何缰绳下都能跑。

延伸阅读：ReAct、CodeAct、SWE-agent 论文；MCP 规范；OpenHands 源码；各家公开的 agent system prompt。读完这些，你对「缰绳」的理解就超过了绝大多数只看榜单的人。
